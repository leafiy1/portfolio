## 1. 项目背景

- **起因**：为作品集打造一款"能讲出完整产品故事"的 Web 游戏作品，主题为《迷宫饭》同人休闲游戏（玩法+前端+UI+美术），并作为"AI 多智能体协作开发"流程的代表作。
- **初始版本**：v2.1 单文件游戏，已有 5 层迷宫 / 25 魔物 / 20 菜谱 / 30 事件 / 20 成就，含战斗、烹饪、装备、存档、周目等系统。
- **痛点（面试反馈）**：**"内容少、粗糙"**——具体表现为：
  1. 内容纵深不足（只有 5 层，终局感弱，周目循环缺乏新目标）；
  2. 多个系统"看似有、实则半成品"：隐藏菜谱无法烹饪、部分事件渲染 undefined、图鉴/评级/诅咒反馈为空面板、若干成就永远无法解锁；
  3. 缺少产品侧文档，无法向面试官证明"设计能力"而不只是"会写代码"。

## 2. 我的角色

> 定位：**产品策划 + 验收负责人**（兼任全栈实现，便于快速闭环）。

| 职责 | 具体动作 |
|------|----------|
| 需求拆解 | 把"内容少、粗糙"翻译成可验收的需求清单：内容深化 × 系统闭环 × 体验打磨 × 文档交付 |
| 范围界定 | 定红线：只改游戏目录、不动 OST/其他作品文件、不引入外部依赖、file:// 与 HTTP 双环境可玩 |

| 风险控制 | 大改造前先做基线验收（截图/DOM 检查/控制台），改后逐项回归 |

## 3. 关键决策（含取舍）

### 决策 1：第六层用"同一套数值公式"续写，而不是重做数值
- **背景**：新增层数/BOSS 需要强度合理。若另造公式，会破坏既有平衡与文档口径。
- **方案**：沿用 `魔物强度 = 周目×1.3 × (1+(层数-1)×0.18) × (1+BOSS×0.3)`，新增第六层小怪倍率 1.9、饕宴王倍率 2.2。
- **结果**：1 周目饕宴王 HP1320/ATK88，恰好落在"需要深度养成后才能挑战"的难度带，周目 ×1.3 后依旧有挑战性。

### 决策 2：终局 BOSS 后移，周目循环更有"仪式感"
- **背景**：原版击败守锅巨像即"通关"，内容止步于第五层。
- **方案**：守锅巨像改为"开启黄金盛宴厅"的守门者；新增第六层终局 BOSS 饕宴王，击败它才触发通关+周目循环；主线任务链扩展 q1→q7。
- **取舍**：改动 BOSS 结算逻辑（通关标记从守锅巨像移到饕宴王），换来"终局感+收集新目标"。

### 决策 3：隐藏菜谱从"摆设"做成"完整闭环"
- **背景**：原版隐藏菜谱只能弹"发现"提示，无法烹饪，相关成就永远不可达成。
- **方案**：实现 发现（食材组合）→ 常驻横幅 → 菜谱列表带"隐藏"标签 → 消耗食材烹饪 → 计入图鉴/成就 的完整链路，并新增 2 道隐藏菜谱。
- **结果**：收集系统"图鉴/菜谱/成就"三件套全部打通。

### 决策 4：把"粗糙"归零——逐项修复可见缺陷
- 事件 ev21–ev30 渲染 undefined、图鉴进度/厨神评级/诅咒反馈空面板、暴击/连击/克制成就计数失效、音效开关缺失、内联 SVG 纹章美术闲置、森西厨具特攻无效等 14 项，全部修复并写入 CHANGELOG。

### 决策 5：验收标准先于实现
- 定义硬性通过条件：`verify_game.cjs` 输出 `CONSOLE_ERRORS: none`，且真实操作流（新游戏→探索→战斗→烹饪→存档→读档）无异常；file:// 与本地 HTTP 双环境验证。

## 5. 复盘

### 做得好的
1. **用公式统一口径**：内容扩展没有破坏既有数值体系，且可被文档化、可被面试官追问。
2. **验收前置**：先定义"零报错+全链路"红线，改造过程每一步可回滚（备份链 v3）。
3. **缺陷归零思维**：不放过"看似有实则废"的功能，隐藏菜谱/空面板/死成就这类隐性粗糙点反而是面试扣分重灾区。

### 可以更好 / 教训
1. **中途返工**：内容插入时多个数据结构写在对象括号之外导致语法错误，说明"批量文本编辑"类操作应先做语法快检（node --check）再做浏览器验证——后续已把语法检查纳入流程。
2. **范围还可更聚焦**：本次新增 31 处内容改动较多，若时间有限，应优先"隐藏菜谱闭环 + 第六层 + 文档"三件事。
3. **数据驱动不足**：目前缺乏真实玩家数据来校准难度曲线（周目×1.3 在高周目是否过陡），下一步应加埋点/试玩收集。

### 独立验收（无记忆新评审 · 2026-08-13）

改造完成后，由**无改造记忆的独立评审**执行全链路操作流验收（新游戏→探索→战斗→烹饪→存档读档→解锁6层→打饕宴王→通关周目），发现并闭环：

| 级别 | 问题 | 处置 |
|------|------|------|
| P0 | 饕宴王技能 `summon` 数据形状错误（对象 vs 数组），`summon.forEach` 必现 TypeError、残宴幽灵永不召唤、团灭时战斗软锁 | 已修复（summon 改数组 + `Array.isArray` 防御），回归测试通过 |
| P2 | 主线任务未随存档持久化（读档 q3→q1） | 已修复（存档新增 Q 字段） |
| P2 | 守锅巨像「已通关」文案残留、OST 数量口径不符、静态计数陈旧 | 已全部修正 |

> 验收结论：P0 归零后，内容数量、数值公式与绝大多数修复经核实为真，达到"作品集能展示"质量线。
> 教训：仅"加载标题画面"的验证脚本覆盖不到战斗路径——**验收必须走到核心玩法的最深处**，这也是本次审查的最大价值。

## 5.5 v2.4 改造复盘：视觉提质 + 内容深化

### 背景
v2.3 解决"内容少、半成品"，v2.4 聚焦面试反馈的另一半——**"粗糙"**。门面优先：先按设计原则重做视觉，再补内容厚度。

### 决策 1：用一套"设计系统"代替零散样式
- **方案**：重写整套 CSS 为设计系统——暖羊皮纸中性色（60%）+ 陶土橙单强调色（10%）+ 金点缀；圆角/阴影/动效统一刻度；字体四级阶梯，正文 ≥15px，消除满屏 11-13px 小字。
- **签名细节**：标题屏盾形纹章、手账便签开场白、厨神评级墨印印章、战斗伤害飘字、成就徽章卡片。
- **取舍**：不引入外部字体/依赖（保持单文件红线），以系统字体栈 + 楷体便签达成"手账风"。

### 决策 2：内容深化不碰数值公式
- 新增 6 个小剧场事件（角色性格化台词 + 原著梗）、2 常规菜谱、1 隐藏菜谱、2 成就、31 条魔物"生态观察"、39 条菜谱"食欲文案"。
- 所有新内容效果沿用既有数值口径（新菜谱 HP+55~130 / 饱腹+45~85），不另造公式。

### 决策 3：玩法反馈细节化
- 伤害飘字（普通/暴击/克制/连击/敌方伤害 5 种样式）、厨神评级墨印印章、成就解锁弹窗、敌人受击抖动 + 血条闪光，均接入真实结算。

## 6. 一句话总结

> 从"能玩但粗糙"到"内容成体系、系统全闭环、文档可追溯"，靠的不是堆功能，而是**先定验收标准，再按产品闭环补齐每一处断裂**——这也是本项目想向面试官传递的方法论。
